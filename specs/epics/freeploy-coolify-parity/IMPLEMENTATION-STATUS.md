## Notes on DP1

- **Reference build environment (DP-3).** nginx.org's apk signing-key URL, which Coolify's `docker/production/Dockerfile` fetches at build time, answered 404 on 2026-11-23 (upstream `main` has the same line). `tools/parity/reference/up.sh` uses upstream's URL when it answers and otherwise a vendored copy of the same key, checked by sha256 (`ff7cf138…`, byte-identical across archived copies 2019 → 2026-10), with a warning in the run. The Coolify application code and image contents are otherwise exactly `91b7e3e`.
- **Visual job runner** is pinned to `ubuntu-24.04`: `ubuntu-latest` is 26.04, for which Playwright 1.56 ships no Chromium.
- **Reference runs.** The first runs looked green but 96 of 100 "captures" were `/onboarding`: a fresh root team has `show_boarding` on and every page redirects there. The seed now skips onboarding (as "Skip setup" does), and capture records any route that lands somewhere else as `redirected`, never as captured. With that: 7/7 fixtures seeded through `/api/v1`; 91 of 188 visual routes captured at desktop and mobile × light and dark; 88 wait for fixtures (applications, services, databases, backups, sources …) that later DP1 tasks and the feature milestones add; 9 redirect by design (e.g. `/subscription` on a self-hosted instance, `/tags` → `/canvas/tags`). At the time, stage was not deployed; it now is (Lumen console only — the `deploy-web` surface lands in DP3), so no route can pass until DP3.
- **Reference API limits (DP-4).** The contract run sets two operator settings on the reference: `API_RATE_LIMIT=100000` and `API_FAILED_REQUEST_RATE_LIMIT=0`. With the defaults, 299 of 330 unauthenticated checks came back 429: the run was measuring Coolify's rate limiter, not its API. Both limiters are Coolify behaviour that Freeploy must reproduce. They get their own parity scenarios in DP9 (`api.rate-limit`, `api.failed-request-throttle`), measured with the limits on. The runner also retries a 429 honouring `Retry-After`, and fails the run if any answer is still 429.
- **Command goldens (DP-6).** 43 cases over pure `bootstrap/helpers` functions, emitted by Coolify itself in the reference container (run 45107418510) and committed as `tools/parity/commands/goldens.json`. Every run re-emits them and fails on any difference. No helper is ported yet, so all 43 are `pending`.
- **Fixtures (DP-7).** The application, scheduled task, PostgreSQL, Redis, backup schedule, S3 storage, one-click service, cloud-init script, GitHub App and GitLab App fixtures are now created through `/api/v1`, with nothing deployed. Visual routes captured: 169 of 188 (was 91). API reads needing a fixture: 19 (was 52). The 19 routes still waiting need a deployment (DP5), a cloud-provider token (DP11), a Gitea app (no create endpoint), or redirect by design. The id mask now requires letters and digits, after a long word of copy (`excludedcontenttypes`) was found masked; IPv4 addresses are masked as they change per runner. Known limitation: ids embedded inside longer text (Traefik label lines, sslip domains) still differ per run. DP5 makes fixture ids deterministic where the API allows, or masks those spans explicitly.
- **Behaviour and the stage target (DP-8, closes DP1).** `behaviour/run.ts` drives a scenario through `/api/v1` and reads the resulting container state from Docker, normalised (fixture ids, digests, short ids, times) so two systems compare field by field. The reference runs it on its own host, the CI runner, which Coolify manages as `localhost`: first scenario `application.dockerimage.deploy`. The Freeploy side reads its server over SSH and needs a test VM (WAITING.md W1); until then the report says "not run". The harness now runs against Freeploy **stage** (`vars.PARITY_TARGET_URL`, `vars.PARITY_TARGET_API_URL`). Stage serves the Lumen console and no Coolify routes or `/api/v1` yet, so every route and read is reported *missing*. That is the "empty stage" DP1 asked for.
- The parity report is published as a workflow artefact and job summary on every run rather than committed back to `main` by CI (branch protection requires a PR for every change). `parity/README.md` is regenerated by `inventory.ts` in the PRs that change rows.

## Notes on DP2

- **Schema.** 75 `deploy` tables generated from the folded final schema (500_deploy_core, #17, applied on stage and prod), plus `org_keys` (510) and a generated delta (520). The first fold missed migrations that loop over table lists (`foreach ([…] as $t) Schema::table($t, …)`, in 16 files). With those unrolled, 520 adds 28 columns and drops 16 that Coolify itself dropped. 500 stays frozen because it is applied; the generator now emits only the delta, and a test holds 520 to it.
- **Tenancy.** Row-level security is forced on every table, for role `deploy_app`. `withOrg()` is the only way the worker reaches the data. Isolation is proven for all 76 tables against a real Postgres (PGlite): own read and write, the other org sees and changes nothing, no cross-org writes, no org means no data, the operator sees all.
- **Encryption.** The 86 columns Coolify encrypts on deploy tables (`deploy/encrypted-columns.ts`, generated from the models' casts) are stored as `fp1` AES-256-GCM ciphertexts under a per-org data key. That key is wrapped by the platform KEK `DEPLOY_ENCRYPTION_KEY` (a Worker secret seeded per environment) and bound to its org and column. Five casts are not here: 2 on tables Lumen owns, and 3 that Coolify declares on columns its own schema never creates (`instance_settings.sentinel_token`, `servers.logdrain_*`; the real columns are on `server_settings`).
- **Worker.** `deploy-core-worker` is live on stage and prod behind `api-edge` `/v1/organizations/{org}/deploy/*` (#18). Unauthenticated requests get 401 at the edge.


## Notes on DP3

- **Porting method.** A page starts from the reference's rendered markup (the parity capture's `desktop-light.html`), turned into JSX by `tools/parity/port/html2tsx.ts`; `tools/parity/port/gen-deploy-web.sh` regenerates every generated file from a capture. Fixture values in the markup (the user's name, the team, the current page) are bound to props by a patch file per markup (`tools/parity/port/patches/*.json`); every rule must match, so a reference change that moves the markup stops the generator instead of leaving a fixture value in the product. Where state changes the markup (the Appearance cards' selected state), the page is ported by hand from the Blade source instead.
- **Signed-in layout (DP-17).** All of what Coolify's layouts put in `<body>` is generated as one component (`LayoutMarkup`): the shell, the reminders, the command palette and the create dialogs (hidden), because the DOM gate counts every form control on the page. Dropdowns open and close as Alpine's do; the command palette, the create dialogs, the team switcher's actions and the mobile sheet are markup only until their own tasks.
- **No notification channels yet.** Coolify shows "No notifications enabled" when the team has none; Freeploy has none until DP9, so the reminder always shows until dismissed for the month, as on the reference.
- **Personal team.** Registration gives the user a team named as Coolify names it, "<name>'s Team". A DP-15 bug created the team under the internal user id; it is now created under the public id, and on every password sign-in as on the other sign-in paths (live on stage: a new user gets "Parity User's Team").
- **Who the capture signs in as (DP-18).** Until DP-17 the reference capture signed in as Coolify's instance root user. A Freeploy tenant is a regular user: their own personal team, no instance settings, an account they can delete. The seed now creates "Parity User" (user@example.com) with its own team, a `localhost` server on the runner (the root team's host and SSH key, copied into the team) and an API token for that team, and the fixtures and the capture use it. Root stays the instance admin, for the DP12 platform-admin pages. The stage counterpart is the same name and address, its password only in `PARITY_TARGET_PASSWORD`. An earlier stage parity user (root@example.com, DP-17) is unused.
- **Edge CORS (DP-18).** The edge allowed only the Lumen console's origin, so a browser on deploy-web could never read sign-in's answer; checks made with curl did not notice, because CORS is a browser rule. deploy-web's workers.dev origin is now allowed per environment.
- **Profile (DP-19).** Name and password work; Livewire's `dispatch('success'|'error')` toasts are Coolify's toast stack (`layout/Toasts.tsx`), and a ValidationException's message is summarised as Laravel does ("… (and 1 more error)"). The danger zone renders Coolify's blocker branch for the team, with deletion itself a later task; the email-change dialog, avatar, 2FA and passkeys render and are later tasks. The reference used to run on http://127.0.0.1, where Coolify offers no passkeys, while stage is HTTPS; since DP-22 it is reached as `localhost`, where Coolify offers them, as stage does.
- **First signed-in pages through the gate (DP-21's run).** `/profile` and `/profile/appearance` pass on stage at desktop and mobile, light and dark, pixels and DOM; `/login`, `/register` and `/forgot-password` still pass. `/two-factor-required` (a team that requires 2FA) is not ported yet.
- **Passkeys (DP-22).** WebAuthn by `@simplewebauthn/server` on the identity worker and `@simplewebauthn/browser` in deploy-web, in place of Coolify's `@laravel/passkeys`; the relying party is deploy-web's host (from `DEPLOY_WEB_URL`); the WebAuthn challenge travels sealed in the request, so there is no challenge table. Registration needs a confirmed password (Fortify passkeys confirmPassword); deletion asks for the password as Coolify's modal does (the full three-step `<x-modal-confirmation>` comes with the component gallery). A passkey sign-in skips 2FA.
- **Two-factor authentication (DP-20).** Fortify's flow with Coolify's options (confirm, confirmPassword): `/v1/auth/password/confirm` (3 hours, per session), enable → confirm with a code → recovery codes, regenerate, disable, and a challenge at password sign-in (by code or recovery code; a used recovery code is replaced). TOTP is RFC 6238 (SHA-1, 6 digits, 30 s, one step of drift, verified against the RFC's vectors) and a code is never accepted twice, as `verifyKeyNewer` does. The secret, the codes and the sign-in challenge are sealed with AES-256-GCM under `IDENTITY_ENCRYPTION_KEY` (a Worker secret seeded per environment, never printed), bound to the user. The screens are DP-21. Verified end to end on stage through the API with a throwaway fake user (qa-2fa-…@example.com, left on stage): 423 until the password is confirmed, Fortify's messages for a wrong password, a bad code and a bad recovery code, setup confirmed with a real TOTP code, a challenge instead of a session at sign-in, a replayed code refused, a recovery code accepted once.
- **Two-factor screens (DP-21).** `/user/confirm-password` is generated from the reference. The /profile section's pending and enabled states and `/two-factor-challenge` are hand-ported from their Blade views, because the capture sees only the "off" state and the challenge needs a pending sign-in; the QR code is Fortify's (192 px, slate on white) drawn with `qrcode-generator`.
- **Unported routes (DP-23).** A route not ported yet sends a signed-out visitor to /login and shows a signed-in user the layout with a notice, instead of an empty page (stage showed a black screen at `/`).
- **Email verification and change (DP-24).** Coolify only enforces verification in Cloud mode; Freeploy is a hosted service, so it applies: a new password account gets Coolify's signed link (60 minutes, `/email/verify/{id}/{sha256(email)}?expires&signature`, signed with HMAC under `IDENTITY_ENCRYPTION_KEY`) and only reaches /verify until it opens it. Accounts that existed before migration 570, and every magic-link or OAuth sign-in, count as verified (those channels prove the address). The email change follows `Profile\Index` exactly: three limiters (1 per 2 minutes per user, 3 per hour per new address, 5 per hour per IP), a 6-digit code hashed at rest and valid 10 minutes, resend after half the expiry, and the request dropped after 10 failed attempts. The inventory now counts a controller action that returns a view as a page (`/verify`, `/auth/link`, the invitation page), which it previously skipped.
- **Custom theme (DP-25).** Coolify's colour engine from `layouts/base.blade.php` (OKLab/OKLCH, WCAG contrast, the 12 presets, the share code) is a module, `lib/custom-theme.ts`; it reproduces Coolify's own default accent value exactly (`#6b16ed` → `oklch(49.65% 0.2709 289.33)`). The dialog is ported from the Blade; while it is closed the page keeps the captured hidden markup the gate compares.
- **Account deletion (DP-25).** Coolify's self-hosted rule, the reference's: a team where the user is the only member must be emptied of projects, servers and Git sources first (Cloud instead deletes them with the account). The account is deactivated and anonymised (credentials, passkeys, 2FA, OAuth links and avatar deleted; sessions revoked; the address freed), not removed, because sessions and security events reference it. Coolify deletes a single-member team; Freeploy cannot delete an organisation yet (DP10), so the copy says the team is left without members instead of claiming it is deleted. The confirmation asks for the email address and the password; the full three-step `<x-modal-confirmation>` comes with the first page that needs it (risks DP-M).
- **Avatar (DP-25).** Coolify's flow: the browser crops to a square and compresses to a 256 px JPEG, the server checks `image|mimes:jpg,jpeg,png,webp|max:5120|dimensions:max 6000`. Freeploy has no object storage bound yet, so the image is kept in Postgres (migration 580) and served by the edge at `/v1/auth/avatar/{usr_…}`.
- **Two-factor required (DP-25).** `/two-factor-required` is generated from the reference. The reference escapes the team name twice ("Parity User&#039;s Team", a Coolify bug); Freeploy shows the apostrophe, a known, listed difference.
- **Component gallery: deferred** by the owner on 2026-11-24 (risks DP-M). Coolify has no gallery page to compare with; components are compared on the pages that render them.
- **DP3 closed (DP-26).** Routes through the gate on stage (CI's pixel gate; DOM and copy also checked from a workstation after the last deploy): `/login`, `/register`, `/forgot-password`, `/profile/appearance` pass; `/user/confirm-password`, `/two-factor-required`, `/verify`, `/profile` were fixed in DP-26 to the remaining causes below. Every difference left is listed with its cause:
  - `/profile` danger zone: the reference's team holds the fixture project and server, so Coolify shows its "Delete all projects…" blocker; Freeploy's team holds nothing until fixtures can be applied to Freeploy (projects and servers, DP4/DP5; `/api/v1`, DP9).
  - `/two-factor-required`: Coolify escapes the team name twice ("Parity User&#039;s Team"); Freeploy shows the apostrophe.
  - `/login` "Passkeys are not supported in this browser.": shown by Coolify's `@laravel/passkeys` (and by Freeploy) in browsers without passkey autofill, such as the headless Chromium CI uses; in a browser with autofill neither shows it.
  - `/reset-password/{token}` is captured only with a fixture token; it renders on both.
  - Email is not delivered on stage yet (WAITING W5), so verification is not enforced there (`REQUIRE_EMAIL_VERIFICATION=false`) and the email-change code and reset links cannot be completed by a person on stage; the flows are covered by tests and the API checks above.
- **Account rate limits (DP-26).** Every `/v1/auth/*` call used the edge's tight `auth` limit (10 a minute), and one /profile load now makes about six of them, so a user was refused within a minute. Calls on a signed-in user's own account (session, profile, 2FA state, passkey list, email-change state, deletion info, avatar) now use an `account` family at the ordinary 60 a minute; every step that checks a secret (sign-in, registration, reset, password confirm and change, 2FA confirm and challenge, passkey sign-in, email-change code, account deletion, OAuth) keeps the tight limit.
- **Faster parity (DP-25).** CI reuses the reference capture of an earlier successful run when nothing that shapes the reference changed (the Coolify commit, the harness, the inventory), so a PR only captures and compares Freeploy. Until Freeploy serves `/api/v1` (DP9) nothing else needs a live reference; from DP9, `PARITY_FULL` forces a rebuild. `tools/parity/local-stage.sh <run>` compares stage on a workstation against a CI run's reference capture (the stage user's password comes from the macOS keychain).
## Departures from the design

- **No sponsorship popup.** Coolify shows a monthly "Love Coolify? Support our work" popup (`livewire/layout-popups`, instance setting `is_sponsorship_popup_enabled`). Freeploy does not: it asks users to sponsor coollabs.io, which would imply affiliation. The setting exists as a platform-admin setting defaulting to off, and the reference turns it off before capture so screens compare like with like.
