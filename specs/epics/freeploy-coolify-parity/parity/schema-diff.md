## Method

- **Coolify.** All 531 migrations of the pinned commit were run by Laravel's own migrator on PostgreSQL 16, and the
  catalogs were dumped to `packages/db/scripts/coolify-schema/coolify-schema.json` (its README has the commands). Nothing is

- **Compared per table:** every column (type, length, nullability, default, auto-increment), the primary key, every unique and
  non-unique index (columns, order, method, predicate), every CHECK constraint, the storage options and the foreign keys.

   - `users` — Lumen owns it (risks DP-J): identity, membership, billing and events hold these facts.
2. **Tables Coolify does not have (1).** `org_keys` — the per-org data key that wraps the encrypted columns (510_deploy_org_keys); Coolify encrypts with one APP_KEY.
3. **`team_id` → `org_id` (24 columns).** Coolify's `bigint` team reference is the Lumen organization, `uuid NOT NULL`; an index or
   unique index on `team_id` is compared as one on `org_id`.
4. **`org_id` added (51 tables)** where Coolify scopes a row only through its parent (risks DP-I), with an index on it
   (70 indexes Coolify has no counterpart for) and forced row-level security on every table.
5. **No foreign-key constraints (62 in Coolify).** The references are plain columns (generate-deploy-schema.ts: some point at tables
   Lumen owns; integrity is kept by the ported write paths, which also do what `ON DELETE CASCADE` did). 62 of the 62
   referencing column lists are the leading columns of an index in `deploy`.
6. **Indexes Coolify does not have (65 besides those on `org_id`).** The generator's index on each reference column, in place of
   the constraint. An index changes no behaviour.
7. **`uuid` unique where Coolify's is not (2: `environment_variables`, `local_file_volumes`).** The generator makes every `uuid` column unique, because the
   uuid is the public id on every route (design §1.1).
8. **`now()` defaults (14 columns).** Coolify's `->default(now())` freezes the moment the migration ran; `deploy` has
   `CURRENT_TIMESTAMP`, which is what the code relies on for rows created later.
9. **Auto-increment.** Laravel's `id()` is a `bigserial`; `deploy` uses `GENERATED BY DEFAULT AS IDENTITY`. Both are compared as
   auto-increment. Numeric defaults are compared without their cast (`'10'::smallint` is `10`), `NULL::type` as no default.

### Why the 33 unique indexes of `660_deploy_schema_catch_up` cannot fail on existing rows

When the migration was written (2026-11-25) the code on `main`, which stage and prod run, wrote four `deploy` tables: `org_keys`,
`private_keys`, `servers` and `server_settings`. None of them gets a unique index here, so every table below is empty there
until the task named in its row is deployed; from then on the reason given holds.

|---|---|
| `additional_destinations (application_id, server_id, standalone_docker_id)` | attachAdditionalDestination() (DP-58) keeps one row per (application, network): it updates that row when there is one and inserts otherwise. Promoting inserts the former main destination, which repeats a row only if that same network had been attached as an additional one before — the page does not offer it |
